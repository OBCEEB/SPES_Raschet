## 1. Ответы на §11 и принятые решения

### 1.1. Шкала времени пиранометра — UTC. Принято.

Две независимые оценки сходятся на сдвиге ровно 3 ч:

| Оценка | Как есть | Метки +3 ч | Опорная точка |
|---|---:|---:|---|
| Аудит (`audit/timing_impact.json`) | −164,7 / −169,1 мин (зима / прочие) | +15,0 / +10,7 | центроид кривой ясного неба, слот привязан к середине |
| Агент вычислений (`hh_q_only.csv`, 1009 сут) | −183,4 мин | −3,4 | истинный полдень, метка — начало слота |

Разница между оценками — это и есть 15 мин между началом и серединой слота. Остаток +11…+15 мин в аудите объясняется точечной выборкой минуты в :00/:30, приписанной середине слота; после перехода на средние он должен уйти. Если остаток не уйдёт, придётся искать другую причину.

Решение: `PYRANOMETER_FILE_TZ_H = 0.0`, `MSK_H = 3.0`. В `docs/decisions_log.md` записать: документации логгера нет, шкала установлена по геометрии Солнца.

### 1.2. Шкала ASMG — тоже UTC. Принято.

Сверка трёх суток (2023-03-09, 2024-01-09, 2024-06-15; 7 смен облачности) с METAR UUOL (Iowa State, всегда UTC): совпадение по меткам файла, а при гипотезе MSK события расходятся на 3 ч. Инструкция просила 3–5 суток; 3 суток с 7 событиями достаточно.

Решение: `ASMG_FILE_TZ_H = 0.0`. Склейка пиранометр↔ASMG по одинаковым меткам была верной; обе шкалы сдвигаются на +3 ч вместе.

Последствия, которые нужно учесть:
- колонка `obs_time_msk` в старом `hh_station.csv` на деле содержит метку файла (UTC); в новой версии она должна содержать настоящее MSK;
- суточные агрегаты ASMG (облачность за световой день) считать по суткам MSK после перевода.

### 1.3. Получасовки — средние за интервал. Принято; данные это позволяют.

Проверка по сырым минуткам (`audit/ssd_minute_probe.json`): из 48 253 получасовых слотов 89,9 % содержат все 30 минут, 99,77 % — не меньше 24; 1-й процентиль — 28 минут.

Решение:
- среднее всех минут `[t0, t0+30)`;
- слот действителен при `n_min ≥ 24`, колонку `n_min` записывать;
- геометрию считать на `t0 + 15 мин`, как сейчас;
- выборку в :00/:30 не оставлять даже параметром.

Чем являются сами минутные значения (мгновенный отсчёт или среднее за минуту), неизвестно. В статье писать «минутные значения логгера».

### 1.4. SSD — колонка того же логгера; происхождение не установлено. Принято с уточнением.

Агент вычислений прав: SSD — пятая колонка минутного файла, а `load_t_ssd` суммирует её по слоту. Моя проверка по сырым минуткам (`audit/ssd_minute_probe.json`, 682 015 дневных минут при высоте Солнца > 3°) показала три вещи:
- SSD принимает значения от 0 до 60 с, причём в 6,4 % дневных минут — промежуточные. Значит, сияние фиксируется точнее минуты: либо отдельный датчик, либо алгоритм логгера на секундных отсчётах;
- SSD **не** является порогом по минутному GHI. Лучший порог по GHI (≈ 200 Вт/м²) совпадает с SSD > 30 с только в 86,2 % минут;
- порог по минутному kt ≈ 0,35 даёт 92,7 %. Связь с kt сильная, как у любого критерия сияния (DNI > 120 Вт/м²), но не детерминированная.

Решения:
- не писать ни «независимый датчик», ни «доказанная утечка Kt»;
- признак `s` оставить с подписью «продолжительность солнечного сияния, регистрируемая тем же станционным логгером»;
- в статье A **обязательно** приводить варианты моделей приведения с SSD и без SSD. Модель с SSD применима только там, где есть такой же логгер, то есть не для переноса справочника на пункты без наблюдений;
- автору: если найдётся паспорт логгера (модель, метод определения сияния) — дописать.

### 1.5. ΔT(t) — решение по умолчанию, окончательно решает автор.

Агент вычислений решил сам: ΔT = 40 K, сценарий ΔT(t) не строить. Это совпадает с моей инструкцией, когда тепловой модели нет, поэтому принимаю как решение по умолчанию:
- ΔT = 40 K — диагностический фиксированный сценарий;
- в статье B сезонность Gcrit объяснять только через IAM и угол падения, не через температуру;
- ΔT(t) = Tm(t) − Ta(t) — в «Ограничения» и «планируемые работы»;
- Ta вместо Tm не подставлять.

Если у автора есть модель бака или контура (Tm(t)), вопрос открывается заново (§6).
